the problem

An assistant that forgets is an expensive goldfish

I got tired of re-explaining the same context to Claude every morning: last week's decision, the gotcha that cost me a day, which account wants which convention. So I built a brain that learns something once and hands it back at the start of the next session, in whatever project I'm in. The vector database is throwaway. The actual knowledge is markdown in git, so nothing is trapped and I can read my own history with git log.

the ideas worth stealing

Four decisions do the work

01

Recall before acting

Every assistant searches the brain at the start of non-trivial work, so a decision on one account surfaces on the next. Reading first is the half that pays.

02

Markdown is the source of truth

The source of truth is markdown in git. The embedding store is a cache I can wipe and rebuild. Portable, and nothing is locked in.

03

It maintains itself

A daily recall canary, a weekly lint that drafts notes, a contradiction check, and an evolution proposer. The machine drafts. A human promotes.

04

It measures itself

Acceptance (merged over drafts) and cost per accepted note. Unresolved metrics show a dash, never a green zero.

how knowledge moves

Capture is easy, so curation is scheduled

Most of it is automatic. A weekly job mines the week and drops drafts into an inbox that nothing trusts yet. When I say promote the inbox it verifies each draft, merges it, fixes the links, updates the index, and syncs. A human gates only that last step, which is the guardrail against a poisoned note spreading.

how it knows it's working

The agents draft. The merge is the signal

The cloud agents can open a pull request and nothing more. The merge is the acceptance event, and the dashboard tracks whether it's paying off: acceptance rate, and cost per accepted note, $11.98 lifetime so far. Collectors are read-only, and the scope of anything an agent sends comes from my request, never from a page it fetched.

finding other agents

Discovery runs on DNS-AID

The assistants reach their own tools over MCP. Agent-to-agent discovery is a different problem, and I didn't want hardcoded endpoints or a central registry. An agent's endpoint and capabilities are published as SVCB records in ordinary DNS and validated with DNSSEC and DANE.

I wrote the reference implementation from scratch. It is now a Linux Foundation project and an IETF dnsop draft.

the philosophy

agent = model + harness

This is built on one idea: in production the harness, not the model, is where the controllable performance lives, roughly a 6x swing independent of the weights. The recall rule is a system-prompt decision. The two MCP tools are the tool layer. The canary and the health check are verification loops. The inbox-to-promote gate is orchestration and a guardrail at once. The model is the tiebreaker, and because the markdown is canonical, swapping it loses nothing.

build your own

Five steps

  1. Stand up a vector-memory service and expose search_memory and add_memory to your assistant over MCP.
  2. Make a git repo of markdown for the real knowledge. Add an inbox for drafts and a folder for weekly reports.
  3. Put three rules in every assistant's system prompt: recall before acting, write durable facts not transient state, never store secrets.
  4. Add two scheduled jobs to start: a daily recall canary and a weekly lint that drafts promotion candidates.
  5. Keep the database disposable. Prove you can wipe it and rebuild from the markdown.
